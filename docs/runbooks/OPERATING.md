# Експлуатація

Усе, що потрібно, щоб підняти систему, покласти в неї документи й переконатися, що
вона працює. Команди виконуються з кореня репозиторію.

## 1. Підняти

```bash
make api-install          # один раз: віртуальне середовище і залежності
make api-run              # http://127.0.0.1:8000
```

Перевірка живості й готовності — це різні речі:

```bash
curl -s localhost:8000/health   # {"status":"ok"} — процес відповідає
curl -s localhost:8000/ready    # 503, доки корпус порожній: працює ≠ обслуговує
```

`/ready` повертає 503 і `"status":"degraded"`, якщо корпус порожній **або** сховище
несправне. Це стан «система жива, але відповідати їй нема з чого» — саме той, який
має бачити черговий, а не здогадуватися.

## 2. Покласти документ

```bash
python3 scripts/ingest.py наказ.md \
  --title "Наказ №123" \
  --authority official_ua \
  --tier public
```

Документ потрапляє в корпус у стані `quarantined` і **не цитується**. Це не
затримка — це вимога: між файлом і відповіддю стоїть людина.

Затвердити може лише рецензент, і це окремий свідомий крок:

```bash
python3 scripts/ingest.py наказ.md --title "Наказ №123" \
  --authority official_ua --review approved
```

Повторний запуск на тому самому файлі безпечний: ідентичність фрагмента походить
від його змісту, тож вставляється нуль рядків і це видно у звіті (`inserted: 0`).

Замінити редакцію:

```bash
python3 scripts/ingest.py --supersede <стара-версія> --replacement <нова-версія>
```

Скасована редакція лишається в сховищі, але перестає керувати відповіддю.

Формати: `.txt` і `.md`. PDF відхиляється прямо — витягу тексту ще немає, а
напівпрочитаний PDF дає фрагменти, які виглядають як текст і не означають нічого.

## 3. Спитати

```bash
curl -s localhost:8000/v1/answers \
  -H 'Content-Type: application/json' \
  -d '{"text":"хто визначає черговість евакуації"}' | jq
```

Чотири можливі відповіді, і кожна означає рівно те, що написано:

| статус | що сталося |
|---|---|
| `answered` | кожне твердження має посилання на конкретний фрагмент |
| `insufficient_evidence` | у затвердженому корпусі немає підстав |
| `access_denied` | запитано корпус, якого читач не має; індекс не чіпали |
| `requires_human_review` | відповідь затримано: нецитоване твердження, збій генератора, порушення доступу |

Рівень доступу **не передається в запиті** — він походить від токена:

```bash
curl -s localhost:8000/v1/answers -H 'Authorization: Bearer <token>' ...
```

Спроба назвати власний рівень (`"user_tier": "restricted"`) відхиляється з 422.

## 4. Калібрування порогу

Поріг, за яким система замовкає, не вибирається на око:

```bash
make calibration     # перевірити, що заморожене число відтворюється
make recalibrate     # перерахувати після зміни евал-набору
```

Правило записане у `config/calibration.json` разом із хешем набору, на якому число
отримане. CI виконує `--verify`: якщо число перестало відтворюватись, це червоний
пайплайн, а не тихий дрейф.

## 5. Коли щось ламається

- **Пошкоджена база.** Файл автоматично відкладається як `korpus.corrupt-<час>`, а
  корпус відбудовується з журналу `data/corpus-journal.jsonl`. `/ready` покаже
  `"store_recovered": true` — це слід, який треба розслідувати, а не прибрати.
- **Генератор мовчить.** Після 5 підряд збоїв запобіжник розмикається на 30 секунд:
  відповіді затримуються миттєво, замість того щоб кожна чекала таймауту.
  `/ready` покаже `"generator_circuit": "open"`.
- **Перевантаження.** Ліміт частоти діє на суб'єкта: 30 запитів у сплеску, далі 1/с.
  Перевищення повертає 429 у тій самій формі відповіді, а не окремим форматом помилки.
- **Внутрішня помилка.** Клієнт отримує 500 із тим самим об'єктом відповіді
  (`requires_human_review`) без сліду стека; подія лягає в аудит.

## 6. Перевірити все перед злиттям

```bash
make gate
```

Це `check` (валідація репозиторію, тести, ruff, mypy --strict, eslint, tsc) плюс
покриття з порогом, евали, звірка калібрування і мутаційний гейт.
