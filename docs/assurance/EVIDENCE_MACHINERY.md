Це не продукт. Це рантайм, який вирішує, чи має проєкт **право** сказати PASS.

| шар | де живе | одиниця обліку |
|---|---|---|
| лани | `Makefile` (223 цілі) | ціль make |
| живучість гейтів | `config/operations/gate-liveness.yaml` + `~/neuron7x-verdict` | отрута |

## 2. Живучість гейтів

Рушій — **зовнішній пакет** `~/neuron7x-verdict`. Конфіг у КОРПУСі, закон поза ним.

**Виміряний склад (02.09.2026, ранок):** 13 гейтів · 36 отрут · 4 `equivalent` · 0 гейтів
без отрут. Види: `replace` 21 · `append` 8 · `delete` 6 · `create` 1 (`chmod` підтримується,
не вжито). Того ж дня додано чотирнадцятий гейт `corpus-path-declarations` (+3 отрути,
з них одна метаморфна). Поточні значення — виміри `liveness_gates` і `liveness_poisons`
у `config/operations/release-surface.json`.

### 2.1 Вироки

```python
if not results:            return Liveness.UNTESTED
accepted = any(r.passed for r in results)
refused  = any(not r.passed for r in results)
if accepted and refused:   return Liveness.ARMED
return Liveness.ONE_WAY_PASS if accepted else Liveness.ONE_WAY_FAIL
```

| вирок | означає | чому відмова |
|---|---|---|
| `ARMED` | спостережено і як такий, що приймає, і як такий, що відхиляє | єдиний прохідний стан |
| `ONE_WAY_PASS` | не відхилив НІЧОГО | константа в одязі гейта |
| `ONE_WAY_FAIL` | не прийняв НІЧОГО | важче помітити — **виглядає як строгість** |
| `UNTESTED` | жодної проби | ≠ пройденому; друге ім'я — **vacuity** (Beer et al., CAV 1997) |

**Позитивний контроль первинний**: `run_gates` завжди додає `Probe("чистий стан",
expect_pass=True)` ПЕРЕД отрутами. Без нього гейт, що відхиляє все, набрав би повний бал
на самих отрутах.

Код виходу CLI: `ARMED` **із розбіжністю не зараховується**.

### 2.2 Навіщо `equivalent: true` окремо

Отрути питають: **«що проходить, хоч не мало б?»**
Ніщо інше не питає: **«що відхилено, хоч не мало б?»**

`equivalent: true` — метаморфна проба: той САМИЙ вхід, записаний інакше. Гейт МУСИТЬ
прийняти. Розбіжність тут — **ХИБНЕ ВІДХИЛЕННЯ**, і `false_rejections` тримає їх окремо
від `disagreements`.

Ціна асиметрична: **відмова приходить у вигляді факту** («dead», «STALE»), і факт ніхто
не переміряє. Чотири відкриті документи вибули з корпусу, бо мережеву помилку записали
як `dead`.

Чотири варіації в дереві: ISO-дата з часом · модуль СКОРОТИВСЯ · кінцевий пробіл ·
зайвий переведений рядок.

### 2.3 Негативні контролі всередині самих отрут

| вид | контроль |
|---|---|
| `append` | ENOENT, якщо цілі немає |
| `replace` | `LookupError`, якщо `find` не знайдено — **застаріла отрута нічого не перевіряє й мусить упасти голосно** |
| `replace` при >1 збігу | `LookupError` без `occurrence` — інакше `str.replace(..., 1)` мовчки влучає в перший |
| `create` | `LookupError`, якщо файл уже існує |
| `delete` | `LookupError`, якщо файла й так немає |

## 3. Провенанс і свіжість

### 3.1 ДВА дайджести, які НЕ МОЖНА порівнювати

| | `provenance.compute_source_digest` | `source_digest.source_tree_digest` |
|---|---|---|

| обсяг | 20 оголошених шляхів | усе відстежене мінус `reports/`, `var/`, `dist/` |

Обидва писалися в поле з іменем `source_tree_sha256`. Звіт, підписаний одним і
перевірений проти другого, читається як `unbound` — **повідомлення про те, що дерево
змінилось, тоді як порівняли два різні виміри**. Лікування — не однакове число, а
`digest_scope` поруч зі значенням і порівняння ОБЛАСТЕЙ перед хешами.

### 3.2 Три капкани, вже закодовані

- **Обхід ФС ≠ властивість коміту.** 53 незатрековані файли всередині `config/` робили
  локальний дайджест іншим за дайджест коміту: `make validate` зелений тут, червоний у
  чистому клоні тієї ж ревізії.
- **Фільтр вимикався МОВЧКИ.** У продакшенному образі git відсутній за побудовою. Та сама
  функція на тому самому дереві дала різні значення на хості й у контейнері — контейнер
  побачив на дев'ять файлів більше (`infra/secrets/*.txt`). Запасне джерело —
  `SOURCE_MANIFEST.json`; без git і без маніфеста — **`None` і відмова**, бо обсяг
  невідомий, а не «дорівнює всьому».
- **Друге означення — ВИДАЛЕНЕ, не полагоджене.** `source_digest._included` розходився з

  був нестабільний за побудовою**. Додати шість імен полагодило б сьогоднішню різницю;
  видалення другого означення робить різницю неможливою.

### 4.1 Вісім вимірів

**ПОІМЕННО** — `answer_axes` 16 · `hard_predicates` 14 · `liveness_gates` ·
`lane_validate_targets` (32 передумови + 3 скрипти рецепта станом на §1.2; далі

**ЛІЧИЛЬНИКОМ** — `mutants` · `budgeted_modules` · `liveness_poisons` ·
`scripts_declaring_selftest`. Значення читаються з дерева самим гейтом; оголошені —
у `release-surface.json`.

### 4.2 Чому чотири поіменно, а чотири лічильником

**Лічильник ловить лише ЧИСТЕ скорочення.** Прибрати одну вісь і додати іншу — число
не рухається, хоча властивість, яку боронила прибрана, не міряє вже ніхто. Селфтест має
цей випадок: `{"answer_axes": ["a","c"]}` проти `["a","b"]` — **однакова кількість, FAIL**.

**Великі виміри — кількістю з одностороннім ратчетом**, бо перелічувати сотні
ідентифікаторів у конфізі = **друге оголошення того самого факту**, і воно розійдеться мовчки.

**Зростання — не помилка, але й не мовчання.** Нові члени звітуються як `grown` і НЕ
рухають декларацію: `--record` — окремий крок, інакше гейт сам собі підписував би нову
поверхню.

### 4.3 Що вимагає виправдання

Усі чотири поля обов'язкові: `dimension`, `member`, `on`, `reason`. Запис без причини й
дати не є названим. Для `COUNTED` прибрати N мутантів = N записів по чотири поля.

Поточно: `"removed": []`. Та сама дисципліна, що `module-budget.raised` — **рішення
лишається можливим, невидимим ні**.

## 5. Мутаційний каталог

**203 файли · 118 із повною копією дерева.** Кількість мутантів рухома (574 вранці
02.09.2026, 579 увечері) — вона є виміром `mutants` у `release-surface.json`, і саме
тому вкарбовувати її вдруге тут не можна.

### 5.1 Правило унікальності якоря

```python
count = original.count(mutant.old)
if count != 1:
    return {"status": "INVALID", "reason": "mutation target must occur exactly once"}
```

**Не «мінімум один» і не «перший». Рівно один.** До 05.08.2026 предикат `M05` траплявся
двічі — у проєкції пошуку й у `list_documents`. Одна підстановка мутувала обидва, і тест
на пошук убивав мутанта. **Два входження під одним мутантом — це не два покриті місця
виклику.** Після розділення предикат листингу лишився без нічого й мутант вижив.

### 5.2 Чому INVALID небезпечний і чим це закрито

`INVALID` не зараховується ні до `killed`, ні до `valid_mutants` — тобто `mutation_score`
лишався б `1.000`. 03.08.2026 лінт переніс переноси рядків, чотири безпекові мутанти
стали INVALID, і **звіт читався як 1.000**.

Два запобіжники: **друге число** `mutation_score_over_catalogue = killed / len(results)`
(ділить на ВЕСЬ каталог) і **код виходу** `0 if score == 1.0 and valid_mutants == expected`.

Статуси з коду виходу pytest: `0 → SURVIVED`, `1 → KILLED`, **усе інше → `ERROR`**.
Помилка збірки не кредитується як убивство. Перед мутантами —
`verify_mutation_baseline`: **наявна поломка ніколи не кредитується як убивство мутанта**.

### 5.3 Чому `--only` пише в інший файл

`main()` розгалужується на `if args.only:` ДО `_run_catalogue`, тож шлях до
`var/mutation-report.json` фізично недосяжний із `--only`. Артефакт несе `"probe": true`.

Причина: `var/mutation-report.json` — **виробник**. `snapshot_assurance` переносить його в
`reports/MUTATION_REPORT.json`, звідки його читають гейт свіжості й вісь `mutation`
(підлога 1.0). Часткова вибірка з трьох мутантів дала б `mutation_score: 1.0`.

Гейт свіжості порівнює **МНОЖИНУ ідентифікаторів**, не кількість:

> ранок: звіт 379 мутантів, каталог 385. вечір: звіт 385, каталог 390. Обидва рази
> «убито 100 %» лишалось на місці й читалось як доказ.

## 6. Осі відповідей

**16 осей.** Живий прогін 02.09: `verdict: PASS`, `unmeasured: []`, найслабша
`paraphrase` 0.75 при підлозі 0.70.

### 6.1 Вирок = найслабша вісь

```python
weakest = min(measured, key=lambda item: item["value"])
```

Не середнє. Середнє ховає рівно те, заради чого профіль існує. Селфтест має цей випадок
буквально: `[0.99, 0.99, 0.10]` при підлозі 0.8 → **FAIL**.

`problems` наповнюється з двох джерел: вісь нижче ВЛАСНОЇ підлоги, і **послаблення без
записаної причини** (`MIN_REASON = 20` символів). «Послабити підлогу» можна, «послабити
мовчки» — ні.

Коди виходу: `{"PASS": 0, "FAIL": 1, "UNKNOWN": 2}`. Розрізняти обов'язково: «не зміг
виміряти» приходить агрегатору як «виміряв і відхилив», якщо обидва віддають 1.

### 6.2 `invert: true` — рівно одна вісь

`boundary_foreign`: `out_of_corpus.rate = 0.20` — частка ЧУЖИХ питань, на які система
відповіла, тобто менше = краще. Після інверсії 0.80 при підлозі 0.75.

Без `invert` вісь із підлогою «не більше ніж» була б другим правилом порівняння в
композиторі. `invert` робить усі 16 осей однонапрямленими, і `min()` лишається **єдиним**
правилом вироку.

### 6.3 Чому UNMEASURED ніколи не стає PASS

Перевірка на `unmeasured` стоїть ПІСЛЯ збору `problems`, але повертає ДО обчислення
`weakest`. Сліпа вісь перебиває і PASS, і FAIL: **вона могла б виявитись найслабшою — а
найслабша і є вироком**.

Шість способів стати UNMEASURED: немає файла · звіт каже `status: UNKNOWN`/`ERROR` ·
вимірювача немає в дереві · SHA вимірювача змінився після звіту · база/корпус/журнал
зрушили (`stale_input`) · вік понад стелю.

Дві деталі:

- **Вік із `ran_at`, не з mtime.** `touch` підробляє mtime; `ran_at` — ні.
- **Вік — сурогат.** Він каже, КОЛИ міряли; питання інше — **чи те, що міряли, ще те
  саме**. Звіт віком 23 год про корпус, змінений п'ять хвилин тому, проходив; звіт віком
  25 год про нерухомий корпус відхилявся. Обидві помилки лікує `stale_input`. Базу беруть
  ту, яку **назвав сам звіт**, а не константу — константа зробила б перевірку правильною
  лише для одного розгортання й неперевірюваною на еталоні.

## 7. Замикання гейтів

> **кожна перевірочна ціль АБО досяжна з `check`, АБО названа в реєстрі — з причиною і датою.**

Корені — **чотири**: `check`, `validate`, `check-deployment`, `check-nightly`. Три різні
бюджети; `validate` названий окремо, бо саме про нього кажуть «зелений».

### 7.1 Шість окремих способів збрехати

| перевірка | FAIL коли |
|---|---|
| `unregistered_gap` | нова перевірочна ціль, яку ніхто не підключив і не назвав |
| `dead_exemption` | запис про ціль, яка НАСПРАВДІ досяжна |
| `ghost_exemption` | запис про ціль, якої в Makefile більше немає |
| `unreasoned_exemption` | причина коротша за 20 символів |
| `duplicate_target` | ціль оголошена двічі З РЕЦЕПТОМ — make мовчки лишає ОСТАННІЙ |
| `unfounded_requirement` | «потребує аргумент» для цілі, чиї змінні всі в `$(if ...)` |

`verdict()`: `FAIL` перебиває, потім `UNKNOWN`, і лише за відсутності обох — `PASS`.
Порожній `declared`, відсутність коренів, відсутній Makefile → **`UNKNOWN`**.

### 7.2 Три нетривіальні місця

- **Ребра з РЕЦЕПТА.** `evidence-refresh` кличе `$(MAKE) dependency-locks` у рецепті.
  Парсер, що читає лише заголовки, оголосив би `dependency-locks` дірою: **перевірка
  досяжності, зроблена наївно, сама стає джерелом хибних дір.**
- **Одиниця обліку — СКРИПТ, не ціль.** Так зараховано 11 цілей.
- **`selftest_only` — обчислення, не запис.** Виняток у реєстрі був би твердженням, яке
  ніхто не переміряє; це — обчислення, яке хибніє разом із рецептом. Зараховано 4.

### 7.3 Реєстр — 18 записів

Множина «перевірочні, не під гейтом» **дорівнює** множині реєстру: симетрична різниця
порожня.

Історія: 31.08.2026 виміряно 193 цілі, 44 перевірочних, **27 не виконувались жодною
дорогою**. Три входи закрили дев'ять → 19 → 16 → 18.

Запис `production-assurance-verify` цінний окремо: **причина в реєстрі — теж неперевірене
твердження**. Попередній текст казав «недосяжна»; вимір показав, що ціль запускається без
аргументів і дає вирок. Той самий клас — запис `release-verify`, виправлений 02.09 (§1.4).

## 8. Предикати готовності

**14 предикатів.** Оцінювач — `production_hard_predicates.py`, реєстр вимог `_REQUIREMENTS`
у КОДІ. `load_hard_predicate_profile` кидає `ValueError`, якщо `set(ids) != set(_REQUIREMENTS)`
або якщо `gate` у профілі ≠ `gate` у вимозі.

### 8.1 Два незалежні стани

> `software_ready` доводить, що репозиторій **уміє** виконати доказ.
> `externally_satisfied` доводить, що рантайм або незалежний контур довіри **справді подав**
> придатний доказ.
> **`software_ready` ніколи не заміняє `externally_satisfied`.**

`externally_satisfied` — три незалежні умови: усі названі перевірки рівно `True`
(відсутнє ≠ True) · `metadata_equals` · **прив'язка** до `compute_source_digest(ROOT)` і
`release_tag()`.

Прив'язка — причина, чому зовнішній доказ **тривіально втрачається**: 29.08.2026 два
предикати були закриті проти дайджесту `24ead5ea`, наступний коміт зсунув дерево, обидва
файли лишились на диску, `externally_satisfied` упав до 0 — **і скрипт усе одно виходив з
0**, бо дивився лише на програмну готовність.

Про `profile == "runtime"`: на робочій машині стоять обидва замки, але інтерпретатор
3.12.3 замість 3.12.13. Без цієї вимоги доказ dev‑машини задовольнив би твердження про
продакшен **рівно тому, що хибної перевірки в ньому немає** — відсутність перевірки
читалася б як її успіх.

### 8.2 Виміряно 02.09 (реліз v0.9.7)

```
predicates_total 14 · software_ready 14 (100 %) · externally_satisfied 0 (0 %)
```

**Одинадцять із чотирнадцяти** вимагають НЕЗАЛЕЖНОГО підпису. Без підпису — чотири, що
закриваються прогоном: `live_postgres_rls` (справжній PostgreSQL),
`real_domain_corpus_tevv`, `production_like_load`, `exact_python_3_12_13_environment`.

### 8.3 Чому реєстр підписантів порожній ЗА ПОБУДОВОЮ

Усі три реєстри — порожні списки, і це **оголошений стан**, не борг:

> Порожній реєстр — це **чесний стан**: жоден ключ ще не внесено, тож жодна атестація не
> перевіряється, тож жодна підстава не знімається. Внесення ключа — **акт того, хто
> приймає систему, а не правка розробника**. Приватний ключ у цьому дереві не лежить і
> лежати не може.

Це **врядування, не інженерія**. Ніякий код не може закрити 11 із 14 предикатів. Порожній
реєстр — те, що робить `externally_satisfied = 0` **чесним нулем**, а не невиміряним станом.

### 8.4 Ратчет

```python
if not FLOOR.is_file():
    raise SystemExit("... a floor that disappears when deleted is not a floor")
if not isinstance(value, int) or isinstance(value, bool):
    raise SystemExit('... a string like "14" compares against nothing and lifts the ratchet in silence')
```

Два способи знищити ратчет — `rm` файла і `"14"` замість `14` — обидва раніше давали код
виходу 0. `isinstance(value, bool)` виключено окремо, бо `True` є `int`.
