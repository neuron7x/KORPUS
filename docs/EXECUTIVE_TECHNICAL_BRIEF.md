# КОРПУС — технічна концепція та фундамент реалізації

## Призначення

«КОРПУС» — цифрова довідкова, навчальна й адміністративна система, яка
перетворює розподілені масиви документів на контрольований інтерфейс пошуку,
відповідей, навчання та підготовки типових документів.

Основний технічний принцип: система спочатку знаходить відповідне затверджене
джерело, а потім формує пояснення з точними посиланнями. За відсутності достатніх
даних вона повертає формалізований статус нестачі доказів.

## Заплановані результати

- пошук за змістом, точною фразою, номером документа, редакцією та категорією;
- відповіді з документом, розділом, сторінкою й цитатою;
- окремі предметні помічники;
- навчальні маршрути, плани занять, питання та контроль прогресу;
- підготовка чернеток документів із перевіркою обов'язкових полів;
- керування версіями, оновленнями та скасуванням документів;
- підтримка слабкого зв'язку через PWA та компактні API-відповіді;
- повний технічний аудит походження відповіді.

## Початковий інформаційний масив

Проведено структурний облік 5 960 файлів у 797 папках: нормативні матеріали,
статути, програми підготовки, інструкторська база, медицина, зв'язок, БПЛА,
інженерне забезпечення, техніка, NATO, психологія, логістика та діловодство.

Під час імпорту кожний файл отримує цифровий відбиток, метадані, категорію,
редакцію, статус перевірки, рівень доступу та незмінні координати фрагментів.

## Архітектура

```text
Web/PWA
  → API та контроль доступу
    → каталог і життєвий цикл документів
    → гібридний пошук і ранжування
    → формування та перевірка відповіді
    → навчальні й документні модулі
    → аудит і телеметрія

PostgreSQL + pgvector | S3-сховище | Redis | OpenTelemetry
                                      ↓
                         змінні LLM/OCR/STT-провайдери
```

Рішення починається як модульний моноліт: це зменшує операційну складність,
зберігаючи чіткі межі модулів і можливість подальшого виділення ingestion,
retrieval та restricted-контурів.

## Життєвий цикл документа

```text
отримано → карантин → технічна перевірка → вилучення тексту
→ метадані → предметна перевірка → затвердження → індексація
→ оновлення | заміна | відкликання
```

Виконувані вкладення не запускаються. Обробка відбувається у відокремленому
середовищі. Попередня і нова редакції не змішуються.

## Пошук і відповідь

1. Визначення ролі, теми й потрібних уточнень.
2. Фільтрація дозволених і чинних документів.
3. Паралельний лексичний і семантичний пошук.
4. Об'єднання результатів, усунення дублів і повторне ранжування.
5. Перевірка достатності джерел.
6. Формування структурованої відповіді.
7. Перевірка кожного твердження щодо цитованого фрагмента.
8. Відображення редакції, сторінки, обмежень і впевненості.

## Контроль якості

Retrieval і generation оцінюються окремо. Базові критерії:

- Recall@10 не нижче 0,90;
- MRR@10 не нижче 0,80;
- точність цитат не нижче 0,95;
- покриття перевірюваних тверджень цитатами не нижче 0,95;
- правильне виявлення питань без відповіді не нижче 0,95;
- відсутність витоку між рівнями доступу;
- контроль p95 затримки, вартості й актуальності індексу.

Кожна зміна моделі, промпту, chunking або ranking проходить той самий
зафіксований набір перевірок.

## Етапи

1. Пілотний корпус із 20–50 перевірених документів.
2. Ingestion, OCR, метадані та гібридний retrieval.
3. Доказові відповіді з цитатами й контрольованою відмовою.
4. Робоче місце інструктора.
5. П'ять найчастіших сімейств документних шаблонів.
6. Контрольована апробація на 50–100 користувачах.
7. Масштабування корпусів, мобільних каналів та організаційних контурів.

## Склад переданого репозиторію

- виконуваний FastAPI API;
- dependency-free offline-capable PWA;
- JSON-контракти документа та відповіді;
- Docker Compose для PostgreSQL/pgvector, Redis, MinIO й OpenTelemetry;
- агентні політики;
- протоколи ingestion, відповіді, інтеграцій, релізу та приймання;
- модель даних, загроз, спостережуваності та відновлення;
- тести, evaluation fixtures і GitHub Actions CI;
- дорожня карта та каталог сервісів.
