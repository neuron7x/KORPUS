# Межі зовнішньої безпекової оцінки

Підстава недопуску **2.5** знімається лише звітом сторонньої організації
(`config/operations/admission-grounds.json`). Цей документ не знімає її і не є оцінкою.
Він існує, щоб оцінка не починалася з нуля: називає межі системи, модель загроз, що вже
перевірено виконуваними тестами, і — окремо — що **не** перевірялося, щоб оцінювач не
витрачав час на здогади про це.

Складено 5 серпня 2026 р. для `integration/canon-v6`.

## 1. Що саме віддається на оцінку

- `apps/api/src/korpus/security/` — OIDC-верифікація, entitlements, браузерні сесії,
  автентичність джерел, сканування, реєстр рецензентів, governance корпусів.
- `apps/api/src/korpus/application/policy.py` — дозволи, межі розкриття, вирішення
  корпусів за запитом.
- `apps/api/src/korpus/infrastructure/repository.py` — SQL-проєкція видачі, RLS для
  PostgreSQL, ланцюг аудиту та зовнішній якір.
- `apps/api/migrations/` — RLS-політики, привілеї ролі застосунку.
- `deploy/`, `infra/`, `docker-compose.yml` — топологія, секрети, мережеві межі.

Поза межами: генератор природної мови (заглушка навмисно, **ADR-0003 «Provider-independent
model ports»**; тут стояло ADR-0005, яке насправді про обмежену вибірку кандидатів у БД —
виправлено 02.09.2026), веб-клієнт як
джерело довіри (він її не має), фізична безпека, персонал.

## 2. Довірчі межі

| Межа | Хто по той бік | Що система припускає |
|---|---|---|
| HTTP | читач, куратор, рецензент, аудитор | нічого: клієнт не керує ані рівнем допуску, ані набором корпусів, ані `as_of` понад дозволене |
| OIDC-провайдер | зовнішня система ідентифікації | підпис, `iss`, `aud`, `kid`, ACR/MFA перевіряються; **ролі й корпуси з токена ігноруються** і беруться з серверного профілю |
| База даних | оператор БД | застосунок працює під роллю найменших привілеїв; `audit_events` без UPDATE/DELETE; RLS відсікає навіть при дефекті застосунку |
| Об'єктне сховище | оператор сховища | вміст адресується хешем; невідповідність хешу — відмова |
| Файли профілів на диску | адміністратор хоста | профілі пінуються хешем; зміна без оновлення піна — відмова обслуговування, не тиха деградація |

## 3. Модель загроз, від якої будувалося

1. Читач із вужчим допуском намагається дістати матеріал ширшого — через запит,
   через підбір ідентифікаторів, через кеш, через метадані відповіді.
2. Куратор із доступом до одного корпусу впливає на видачу в іншому.
3. Власник токена намагається підняти привілеї claims-ами.
4. Той, хто має запис у БД, намагається переписати або обрізати журнал аудиту.
5. Джерело (документ) намагається керувати системою через свій текст.
6. Той, хто відкликаний, продовжує працювати.

## 5. Що НЕ перевірялося

Названо, щоб відсутність знахідки не читалася як чистота.

- Криптографія за межами використання бібліотек: власних примітивів немає, але й
  аналізу сторонніх параметрів (ротація ключів OIDC у часі, стійкість
  `browser_session_key` до витоку) не проводилось.
- Навмисно шкідливі PDF/HTML за межами перевірки типу і пісочниці парсера.
- Поведінка під навантаженням як безпекова властивість (виміряно лише пропускну
  здатність аудиту: ~450 подій/с, `DESTRUCTION_STAGE_2026-08-05.md`).
- Ланцюг постачання залежностей поза `pip-audit`/SBOM у пайплайні.
- Кілька реплік із одним зовнішнім якорем.
- Побічні канали за часом на 404 фрагмента.
- Мережева ізоляція в реальному розгортанні (маніфести валідуються статично).

## 6. Що вважатиметься зняттям підстави 2.5

Звіт сторонньої організації, який:
1. називає перевірене й **не** перевірене окремо;
2. містить відтворення для кожної знахідки;
3. супроводжується атестацією (документ, його SHA-256, хто підписав, коли) — саме її
   вимагає `admission-grounds.json`, і без неї реєстр підставу не зніме.

Внутрішні тести, перелічені вище, підставу не знімають: їх писав той самий процес, що й
код.
